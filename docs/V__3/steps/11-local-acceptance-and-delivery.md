## 环境与执行顺序

1. 冻结实际代码提交/工作树、依赖 lockfile、构建产物、设备/Chrome/Edge 版本与 P0 性能配置。检查新增 V3 脚本真实存在并登记准确命令；本文不编造未实现的 V3 命令或测试数量。
2. 运行前端 test/lint/build（build 包含 tsc）；修改协作/后端时完成其对应检查。既有实际入口如下，从仓库根执行并逐条检查退出码，失败先处理：

   ```powershell
   Push-Location frontend
   npm test
   npm run lint
   npm run build
   Pop-Location
   Push-Location collaboration
   npm test
   Pop-Location
   Push-Location backend
   mvn test
   Pop-Location
   ```

   完整制品可沿用 `./collaboration/scripts/build-step11.ps1`，具体先读当前脚本及[V2 开发指南](../../V__2/development.md)。仅文档变更无需运行上述应用检查；它们是未来实施验收入口。本机应用运行/集成验收必须读取仓库根 `.env`，连接本机 MySQL、MinIO、Redis。禁止 Docker / Docker Compose，禁止输出或提交凭据；构建/算法测试不能代替真实三服务流程。
3. 选择当前本机启动器或既有验收脚本，禁止同时运行占用同端口的 `start:local` 与 Step11 验收。如使用 `npm run start:local`，在 collaboration 目录启动；既有 `node scripts/verify-step11-local.mjs` 只覆盖 V2，不能将其通过标记为 V3 通过。真实浏览器代理操作另遵循仓库现有约定。
4. 使用测试账号/团队/项目和两个真实授权会话；准备原验收矩阵规定的 fixture、受控 Update 顺序、离线资源与容量边界。保留正常源码/状态/事务断言及 ZIP 检查，截图只辅助。测试身份、凭据、恢复私有片段和本机备份不得进入公开证据。
5. 先执行全部 AC，再核对 FR/NFR 与 P0 风险台账；任何误写、部分提交、静默遗漏、执行隔离绕过或无法恢复先修复并重跑受影响项。不能把核心失败改为“后续”或仅写“已知限制”。范围调整须有具体决策并同步需求/验收；其他项无需无条件重跑，除非修改影响它们。
